# Workspace revisions

Workspace modules, skills, and filesystem edits made through `ws.fs` keep a content-addressed history under `.mypr/revisions/`. A successful tracked write records the previous file on the first change and then records each new content hash. Repeating a write with the same content does not add another history entry. Dry runs and failed compare-and-swap writes do not change history.

If a resource write succeeds but its history index write fails, mypr compares the exact planned index hash with the index on disk. A confirmed commit is reported as success. If the index is unchanged, mypr conditionally restores the previous file, or removes a newly created file, only while the target still matches the attempted write. If another process changed the target, that edit is preserved and the error includes the prior and attempted revision hashes. If a concurrent index change makes the outcome uncertain, mypr leaves the target in place and asks the caller to inspect history before retrying. This applies to single-file writes and shared multi-file transactions, including patches, replacements, AST rewrites, and LSP edits. Batch failures with an uncertain history outcome preserve recovery backups and report their paths. Content blobs are stored before the resource write, so `read_revision(name, hash)` can recover a verified blob even when its index entry was not committed; the response marks this with `recorded: false`. A missing prior file is reported as `absent`.

Use `await ws.modules.history("name")` or `await ws.skills.history("name")` to list the newest revisions first. The default page contains 20 entries; `limit` accepts 1–100. When `has_more` is true, pass `next_cursor` as `cursor` to fetch older entries. Each entry contains a stable sequence number, SHA-256 revision, byte size, and recording time.

`await ws.modules.read_revision("name", revision)` and `await ws.skills.read_revision("name", revision)` return a bounded UTF-8 page. The default page is 32 KiB; `max_bytes` accepts up to 1 MiB. Pass the returned `next_cursor` as `start_byte` to continue. A page may exceed `max_bytes` by up to three bytes when needed to include one complete Unicode character. Revision objects are checked against their SHA-256 name before they are returned.

Restore with `await ws.modules.restore("name", revision, expected_hash=current_hash)` or `await ws.skills.restore("name", revision, expected_hash=current_hash)`. Supplying the current file hash is required when the file exists. A missing file can be restored with `expected_hash=None`. Restore validates Python syntax or skill metadata, writes atomically, and records the transition. It does not load, reload, or otherwise activate a module; existing Python references remain unchanged until an explicit `load()` or `reload()`.

Filesystem history uses `await ws.fs.history(path=...)`, `await ws.fs.read_revision(path, revision)`, and `await ws.fs.restore(path, revision, expected_hash=current_hash)`. It records text and binary writes, creates, deletes, moves, and copies made through the filesystem API. A deleted file has the recorded revision `"absent"`; `read_revision()` returns an empty `absent` result for it. Restore requires the current revision precondition when the target exists and records the restoration as a new transition. External edits are detected by the precondition but are not continuously watched or added to history automatically.

Revision objects are plain bytes named by their SHA-256 hash. Per-resource JSON indexes contain only hashes, sizes, sequence numbers, and timestamps. The history is local to the workspace and does not snapshot unrelated files. The latest `revision_keep` revisions per resource (50 by default) and current content are protected by automatic cleanup. Older entries become eligible after 30 days when the managed-data target is exceeded. The metadata index is capped at 16 MiB per resource and individual stored revisions at 64 MiB. Shared blobs remain while a retained history, task result, or transaction references them.
